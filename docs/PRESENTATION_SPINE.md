## 0. 전제 — 심사자가 바뀌었다

**심사자 = 채용 담당. 인사팀과 기술 면접관이 같은 자리에 동석한다** (daria 확인 2026-08-06).

따라서 **평가 대상은 제품이 아니라 사람이다.** 제품은 미완성이어도 되지만
**판단력은 미완성이면 안 된다.** 이 전제가 아래 모든 선택을 지배한다.

산출물 특강 자료가 같은 말을 한다:

> 최종 결과물도 중요하지만, **어떻게 만들었고, 왜 만들었는지**를 면접관은 더 중요하게 봅니다.
> …어떤 **고민**, 어떤 **이슈**, 어떤 **노력**, 어떤 **개선안**을 만들었는지 스토리텔링이 더 중요합니다.
> 즉, **"이거 해봤어요"보다 "이런 고민과 시도를 끊임없이 했어요"가 더 좋습니다.**
> — 산출물 특강 p.3

**NDA로 설문이 죽은 것은 정확히 "어떤 이슈가 있었는지"에 해당한다.** 감출 항목이 아니라
자료가 요구하는 항목이다.

## 2. Key Accelerator — 정의와 자리 (확정 2026-08-06)

### 정의 (발표에서 먼저 말할 것)

> **"저는 Key Accelerator를 Pain 세 개의 공통 원인을 치는 단일 지렛대로 정의했습니다."**

사내 정의와 미세하게 달라도 **"다르게 정의했구나"**로 끝난다.
정의를 밝히지 않으면 **"잘못 썼구나"**가 된다. 반드시 먼저 말한다.

### 왜 이 자리인가

accelerator는 "좋은 해법"이 아니라 **"적은 힘으로 많이 움직이는 지점"**이다.
Pain 3개를 각각 세 번 고치는 대신 **공통 원인 한 곳**을 친다:

> 세 Pain의 공통 원인: 홈 프로필이 **클라우드 계정과 앱에 종속된 구조.**
> 서버가 죽으면 집이 죽고(P-1), 앱이 리셋되면 설정이 죽고(P-2),
> 프로필이 서버에 있으니 개인정보 수집이 강제된다(P-3).
> → 온바디 귀속 + 로컬 통신으로 **P-1·P-2·P-3을 단일 아키텍처로 해소**
> — [CX_DEFINITION](CX_DEFINITION.md)

**P-1만 풀었으면 이 단어를 못 쓴다. 셋을 동시에 푸니까 쓴다.** 단어의 원뜻과 데이터가 맞물린다.

### 산출물 순서가 이 자리를 뒷받침한다

산출물 특강 p.6~7의 순서는 **CX 보고서(문제 정의) → PRD & MVP(최소 완성 핵심 기능 범위)**다.
Key Accelerator는 **그 둘을 잇는 다리** — "왜 이 기능 범위만 최소로 골랐는가"의 답이다.

> CX 보고서(Pain·POV) → **Key Accelerator** → PRD·MVP 범위 → 유스케이스 → …

⚠️ **주의**: "Key Accelerator"는 산출물 특강 자료 44페이지 전수에 **등장하지 않는다**(2026-08-06 확인).
LG 공개 자료 검색에서도 확인되지 않았다. **사내 용어로 취급하고 위 정의 선언을 반드시 동반한다.**

## 3. MVP 용어 — 산출물 특강 정의를 정본으로 (daria 확정 2026-08-06)

**심사 가이드가 우선한다.**

> **MVP** (Minimum Viable Product) = 이번 프로젝트에서 **최소한으로 완성할 핵심 기능 범위**
> — 산출물 특강 p.7

| 쓰임 | 판정 |
|---|---|
| 산출물로서 **"MVP 범위"** — 최소 완성 기능 범위 정의 | ✅ **쓴다.** 심사 가이드가 요구하는 산출물 |
| 성숙도 라벨로서 **"우리는 MVP다 / MVP를 만들었다"** | ❌ 여전히 금지 — 실사용자 0명·미출시 |

**두 개는 다른 말이다.** 산출물 특강의 MVP는 **스코프 정의**이고,
[MATURITY_POSITION §5](MATURITY_POSITION.md)가 금지한 MVP는 **고객 검증 단계**다.
[§7.1의 파일럿 동음이의 처리](MATURITY_POSITION.md)와 같은 구조로 다룬다.

> 발표에서 "MVP"라 말할 때는 **"MVP 범위"**로 한정해 말한다.
> 단독으로 "MVP를 만들었다"고 하면 제품 단계로 오해된다.

## 4. 💣 ThinQ API 대응 (2024-12 공식 개방)

산출물 특강 p.42~44에 LG가 ThinQ API를 공식 개방한 사실과 접근 경로가 정리돼 있다:
[LG Developer](https://developer.lge.com/) · [Smart Solution API](https://smartsolution.developer.lge.com/) ·
[ThinQ Connect API](https://smartsolution.developer.lge.com/en/apiManage/thinq_connect) ·
[PAT 토큰](https://connect-pat.lgthinq.com/) · [pythinqconnect SDK](https://github.com/thinq-connect/pythinqconnect) ·
[Home Assistant 연동](https://www.home-assistant.io/integrations/lg_thinq/)

### ⚠️ 핵심 — 이 API는 클라우드 경유다

> 사용자 요청 → **서버 요청** → LG ThinQ API → 실제 가전 제어
> — 산출물 특강 p.42

**이 API를 주 전송 경로로 쓰면 P-1(클라우드 SPOF)을 그대로 재현한다.**
우리가 43.4%로 지적한 바로 그 구조다. **온바디 논지와 정면으로 충돌한다.**

### 예상 질문 (거의 확실히 나온다)

> **"ThinQ API 공개됐는데 왜 안 쓰셨어요?"**

**답변 (확정):**

> **"그 API가 바로 저희가 지적한 구조입니다. 서버를 경유하니까 서버가 죽으면 똑같이 집이 죽습니다.
> 저희 논지는 그 경로를 끊는 것이라 주 전송에는 쓸 수 없습니다."**

### 연동 방향 — **A안 확정** (daria 2026-08-06)

| 안 | 역할 | 판정 |
|---|---|---|
| **A. 대조군·실증 장치** | ThinQ API로 실기기를 연결한 뒤 **서버를 끊고 죽는 것을 실제로 보여준다.** 그 옆에서 온바디는 살아남는다 | ✅ **채택** |
| B. 보조 경로(fallback) | 온바디가 주경로, 원격만 ThinQ API | 보류 — A와 병행 가능하나 "원격은 클라우드, 홈 프로필은 온바디" 경계를 장표에 명시해야 함 |
| C. 주 전송 경로 | ThinQ API로 제어 구현 | ❌ **채택 불가 — 논지 붕괴** |

같은 API를 **해법이 아니라 문제의 증거로** 쓴다. 그러면 논지를 지키면서
**"공개된 걸 몰라서 안 쓴 게 아니라 알고서 안 썼다"**가 증명된다.

#### ⚠️ A안의 효과 — 정확히 말할 것 (2026-08-06 정정)

초안에서 A안 효과를 "유사 운용환경 근접 → TRL 상승 여지"로 적었으나 **과장이었다.**

> **TRL은 해법의 성숙도다.** A안에서 실기기에 붙는 것은 **문제 쪽**이고,
> **온바디 프로필은 여전히 시뮬레이터에서 돈다.** 해법이 실기기로 올라가지 않았으므로
> **TRL 4는 그대로다.** A안으로 오르는 것은 TRL이 아니라 **POV의 증거 강도**다.

| | A안 이전 | A안 이후 |
|---|---|---|
| POV 근거 | 리뷰 텍스트 43.4% | **실기기에서 구조가 무너지는 것을 실연** |
| 해법 TRL | 4 (시뮬레이터) | **4 (변동 없음)** |

발표에서 **"실기기로 검증했습니다"라고 말하지 마라.** 정확한 표현은
**"문제가 실기기에서도 재현되는 것을 확인했고, 해법은 아직 시뮬레이터 단계입니다."**

#### A안 구현 개요 (다음 세션 착수용)

| # | 항목 | 비고 |
|---|---|---|
| 1 | PAT 토큰 발급 | [connect-pat.lgthinq.com](https://connect-pat.lgthinq.com/) |
| 2 | `pythinqconnect` SDK 설치·연결 | [GitHub](https://github.com/thinq-connect/pythinqconnect) |
| 3 | 기기 1대 연결 → 상태 조회·제어 1회 성공 | 산출물 특강 p.43~44에 기기별 제어 가능 속성표 있음 |
| 4 | **차단 시나리오** — 네트워크 차단 후 같은 제어 재시도 → 실패 확인 | `offline_guard.py` 기존 자산 재사용 검토 |
| 5 | 같은 조건에서 온바디 경로는 동작함을 나란히 보여주는 데모 | 기존 데모 10종에 1종 추가 |
| 6 | 증거 기록 — OFFLINE_EVIDENCE 형식에 맞춰 로그 보존 | 캡처가 아니라 실행 로그 |

> **선행 조건: 실제 LG 가전 1대 + ThinQ 계정 — ✅ 해소(daria 에어컨 보유 확인, 2026-08-06).**
> 구현 부담은 작다 — 제어 로직을 만드는 게 아니라 **연결하고 끊는 것만** 한다.
>
> **단, 이것은 구현 단계 백로그다** (daria 2026-08-06 "지금은 기획단"). 기획 단계에서
> 필요한 것 — 예상 질문 답변(§4)·서사 내 역할(A안) — 은 이 문서로 완결이며,
> 위 6단계는 구현 단계 진입 시 착수한다.

> 📌 참고: 산출물 특강의 다른 팀 예시(LG Able Band, ThinQ 임산부 케어)는 모두
> ThinQ API 위에 얹은 음성 제어 서비스다. **같은 심사 자리에서 우리만 그 아래 구조를 건드린다** —
> 차별점이므로 의도적으로 대비시킨다.

## 5. 전달 구조 — 한 자료, 세 층

인사팀과 기술 면접관이 **동석**하므로 자료를 나누지 않는다. **위아래로 쌓는다.**

| 층 | 대상 | 원칙 |
|---|---|---|
| **위** | 리크루터 | 한 줄 결론. 스캔하면 여기서 멈춘다 |
| **아래** | 기술 면접관 | 근거·수치. 여기서 질문이 나온다 |
| **주머니** | 질문한 사람만 | 장표에 없음. 물으면 그 자리에서 실행 |

**좌우로 놓지 말고 위아래로 쌓을 것** — 나란히 두면 리크루터가 아래층에 걸려 덮는다.

### 예시 — 빈 칸 슬라이드

> **위:** 타깃 검증 — 못 했습니다. NDA로 설문 중단.
> **아래:** 채울 수단은 세 가지 있었고 셋 다 쓰지 않았습니다. 파이프라인이 검증되지 않은
> 입력을 거부하도록 설계돼 있어, 실행 자체가 막힙니다.

기술 면접관이 **"그 거부하는 게 뭐죠?"** 하고 물으면 → 주머니에서 게이트 데모를 꺼낸다.

### 주머니에 넣을 것

1. **게이트 거부 데모** — `synthetic_panel`을 그냥 실행하면 `survey.csv` 해시 없다고 거부.
   슬라이드 캡처가 아니라 **그 자리에서 실행**한다(조작 의심 차단)
2. **분석 도구(MoA·G 감사 체제)** — 자기 보고 신뢰도 폐지 → 감사 점수 97.6.
   "어떻게 일하는 사람인가"의 증거
3. **ThinQ API 대조 실증**(A안 채택 시)
